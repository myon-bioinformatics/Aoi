# 波の当てはめの「ほぼ同点」と計算の丸め（探索・事後）

`../wave_tie_noise.py` を、2013〜2026年の実データ（168 球団年）で走らせた結果です。確定済みの出力（`outputs/season.jsonl` など）と `sakanalytics` は変更していません。**ε の値の扱いも、`EPS_WAVE_TIE` の直し方も決めていません**（PR #24 は触っていません）。

きっかけは、2024年のソフトバンクが「ε = 1e-3 のときだけ選ばれる式が変わる単位」と記録されていて、その入れ替わりの仕組みが分からなかったことと、疑似シーズン側の `wave_osc_base` が、ε の大きさに比例せず 3〜9 単位で動いていたことです。仮説と予想（a)〜(f)）は、**走らせる前に** `../wave_tie_noise.py` の冒頭に書き、予想つきで push してから走らせました。

## 入力と対照

- 試合: 168 球団年、11,886 試合（2013〜2025年 11,028 + 2026年 858）。SHA-256 は `games.jsonl`（2013〜2025年）`b8cf840580b4c7c4d9da3bce59c742fc0ee16e24999d93855fa4153f75cc424a`、`games_2026.jsonl` `2a5c48d89d49d63364a155f5769a2570ff117b8e66d12fc28e1297ab83a2435f`。[wave_eps_trial_results](../wave_eps_trial_results/README.md) と同じ作り方のローカルの表で、試合そのものはコミットしていません（派生した数と集計だけ）
- 対照: 今のコード（float64）と確定済み `season.jsonl` で、2013〜2025年の 156 単位は違う行 0（`wave_tie_noise.json` の `gate` は pass）。2026年の 12 単位は確定済みの行がなく、対照の外
- float64 の再実装（longdouble 版と同じ形で書いた float64）は、今の `wave_fit` と、33,936 回の呼び出しすべてで戻り値が同じでした（不一致 0）。float64 と longdouble の違いは、足し引きを longdouble にしたことだけから来ます

## 読み（この入力で）

- **一定の線では、選ばれる式が当てはまりの良さではなく丸めで決まっていました。** 一定の線はどの式を当てても誤差の2乗和が数学的には 0 で、候補は全部同点のはずです。ソフトバンク 2024 の線では、float64 の誤差の2乗和が候補の間で 6〜7×10^-12 ばらつき、許容 `EPS_WAVE_TIE`（1e-12）より大きいので、「先の式より 1e-12 を超えて小さいときだけ乗り換える」という規則が、丸めの正負で乗り換えます。longdouble では幅が 4×10^-15 以下に収まり、規則どおり最初の式のままになります
- **2024年のソフトバンクの「ε = 1e-3 でだけ式が変わる」は、この読みで説明できました。** 乗り換えたのは 0.03・0.001・1e-12 の 3 つの ε で、ε の影響が滑らかなら並ばない並びでしたが、longdouble では 9 個とも乗り換えません
- **`wave_osc_base` の ε による動きは、丸めを外すと消えました。** longdouble では ε = 1e-3, 1e-6, 1e-9 のどれでも、対照（longdouble の ε なし）と違う単位が 0 です。float64 で動いていた 4 / 10 / 5 単位は、この入力では丸めの側に原因がある、と読めます。動いた単位の中身（どの疑似シーズンの線か）までは見ていません
- **確定済みの値にも、丸めで決まっているものがあります。** 確定済み（float64）と longdouble で、`wave_osc_base` は 168 単位のうち 70 単位で違います。実線の `wave_osc`・`wave_period` は 2018-l と 2024-h の 2 単位で違い、`wave_rmse` は 2018-l で違います。この 2 単位は、結果を見たあとに確かめたところ、実線がどちらも全期間で一定（高さ 6 が 158 点・149 点）でした。一定でない線では、float64 と longdouble で選ばれる式が 32,493 回のうち 1 回も違わず、この入力で丸めに負けているのは一定の線だけです
- 絶対値の許容 1e-12 は、順位の線（値は 1〜6、点は 100 以上）では丸めの大きさと同じです。[第 2 回の事後の確認](../../../../research/epsilon-generality/results-physical/README.md)で見た「値を小さくすると同点でない式まで同点にする」は、同じ根っこ（許容が誤差の2乗和の尺度に合っていない）の逆向きの現れかもしれませんが、ここでは確かめていません

## 限界・していないこと

- longdouble は「より正確な読み」で、正解そのものではありません。幅が 4×10^-15 以下で許容 1e-12 より小さい、というところまでです。一定の線の誤差の2乗和が厳密に 0 であることは、この幅までしか確かめていません
- この入力（野球の順位の線、168 単位、sims 200）での話です。主食価格・物理量の窓や、別の入力で同じ仕組みが起きるかは見ていません
- **直し方は決めていません。** 許容を誤差の2乗和の尺度に合わせる、誤差の2乗和を残差から直接作る、などが考えられますが、どれも試していません。確定済みの出力を作り直す判断も、あなたの合図が出てからです
- 派生した数だけを置いています（試合はコミットしていません）。`wave_tie_noise.json` には、対照で違った単位のラベルを全部書いてあります

## 追記: Python のバージョンでも変わる（結果を見たあとに気づいた。予想は置いていない）

CI の pytest（Python 3.11）で、一定の線の誤差の2乗和が 1e-18 未満という私のテストが落ちました（3.11 では 7e-15）。原因は、組み込みの `sum()` の足し方が 3.12 から変わったことです（`sum([0.1] * 10)` は 3.11 で 0.9999999999999999、3.12 以降で 1.0）。`wave_fit` の閉じた式は `sum()` で誤差の2乗和を作るので、一定の線では丸めで決まる式が 3.11 と 3.12 以降で違いえます。

合成の一定の線 32 本（値 c ∈ {0.7, 1, 2, 2.3, 3, 4, 5, 6} を n ∈ {30, 60, 100, 150} 点。実データではない）に、標準の波の基準で `wave_fit` を当てました（[`wave_flat_by_python.py`](../wave_flat_by_python.py)、出力は [`wave_flat_by_python.json`](wave_flat_by_python.json)）。

| Python | 選ばれた式が 3.12 と違う線（32 本中） |
|---|---|
| 3.11.17 | 6 本（n=60 c=5、n=100 c=4・5・6、n=150 c=5・6） |
| 3.12.3 | 0 |
| 3.13.17 | 0 |
| 3.14.6 | 0 |
| 3.15.0b4 | 0 |

- 3.12 以降の 4 つは 32 本すべてで同じ式を選び、3.11 だけが 6 本で違いました。
- **限り:** 合成の一定の線だけです。確定済みの出力が 3.11 で変わるかは、この確認では分かりません（確定済みの出力を 3.11 で作り直してはいません）。ε の波の基準でも見ていません。ここまでの結果は 3.14（このリポジトリの `.python-version`）で作ったものです。
- この確認は、上の「ほぼ同点が丸めで決まる」という読みを、同じ入力でも計算環境で結果が変わる、という方向に補強する材料です。EPS_WAVE_TIE の直し方は、これまでどおり決めていません。
