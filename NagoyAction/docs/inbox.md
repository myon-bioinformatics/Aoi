# NagoyAction の質問・探索受付

専用Issueの通常コメントで、人・AIエージェントのどちらからでも受け付ける。
受付Issueはリポジトリ変数 `AOI_INBOX_ISSUE` で指定する。

| コメント | 動作 |
|---|---|
| `/ask E25 に阪神 2015 以外の判例はある？` | 保存済みの結果から回答 |
| `/ask {"ask":"has_counterexample","target":"E25"}` | 型を指定して回答。AIエージェントにも同じ入口 |
| `/explore E25` | E25の前件に使われている集合で、Bクラスへの式を探索 |
| `/explore {"sets":["OFF_SHORT","DEF_WORSE"],"max_depth":2}` | 登録済み集合を指定して探索 |
| `/explore all` | 登録済み全集合を候補とする |
| `/status` | 受付件数と直近10 jobの進捗 |
| `/stop 123456789` | 依頼のコメントIDで停止 |

通常の会話には反応しない。1コメントに1コマンド、4000文字まで。
コメント編集は再実行しない。修正した依頼は新しいコメントで投稿する。
質問文の未対応条件・不明なID・不足した結果を「反例なし」にしない。
成立率と除外後の反例一覧は別の値で、`exclude` によって成立率を再計算しない。

## 起動と保存

実行管理はNagoyAction、問い合わせの型と読み取りはQueRyu、式の探索と判定はPythDRagorasが担当する。
ActionsのYAMLは既存の `nagoyaction.py run` を呼ぶ。Dockerの起動・待機・終了も
`NagoyAction/pipelines/inbox.toml` に記載し、Compose設定は `NagoyAction/containers/llama.compose.yml` に置く。
ローカルでも同じ定義を使い、実行した手順は `--receipt` に記録する。

- `research-inbox.yml`: コメント投稿時、および15分間隔で受付を読む。
  `GITHUB_TOKEN` で別のActionsが投稿したコメントも、定期読取りで拾う。
- `research-worker.yml`: 15分間隔で保存された探索依頼を読む。探索は同時に1ジョブ。
  質問受付は別のconcurrency groupで動くので、探索終了を待たない。
- 両方とも既定ブランチのコードをcheckoutする。PRのコードをコメントから実行しない。
- 初回受付時に `aoi-research-state-<cycle>` を空の履歴から作る。そこに依頼・回答・途中結果を保存する。
  取得元へアクセスせず、既存の `season.jsonl` と命題・集合定義だけで計算する。
- 1回のworkerは5時間で新しい処理を止める。workflowは330分で打ち切る。
  30秒または100候補を目安に小分けし、各区切りでローカルに保存する。状態ブランチへの反映は5分ごと・終了時にまとめ、完了通知前にも確定結果を反映する。
  単一候補の処理中は中断しないので、5時間は開始を止める期限。
  候補・結果は100件ずつのファイルへ分割し、1つの巨大な状態ファイルを作らない。
- 次回はcursorから再開。同じ計画・入力指紋は同じjobにまとめる。
  質問の回答も、問い合わせ型・結果ファイル・回答コードの指紋で再利用する。
- 依頼追加と結果保存が重なった場合は、状態ブランチの新しいコミットをrebaseしてからpushする。
  pushに失敗したチェックポイントはActions artifactにも残す。
- 停止は依頼者か管理側が行う。同じjobを別の人も依頼していたら、そちらは継続する。
  停止コメントは受付処理後、workerの次の状態同期（最大約5分＋バッチ処理時間）で反映する。

GitHubの定期実行は遅延・停止することがあるため、常駐サービスの即時性は保証しない。
手動のworkflow dispatchでも再開できる。Botの回答は返信マーカー付きで、再度依頼として読まれない。

## 探索の範囲

既存の `PythDRagoras/logic/sets.py` と `propositions.py` を使用する。
元・逆・裏・対偶、反例、判定不能、焦点球団の覆いを残す。
反例のある式には登録済み集合を `&` で足し、覆えない単位がある式には `|` で道筋を足す。
集合の否定も使う。境界値・新しい列・実行コードは生成しない。

最初に集合名・深さ・候補数上限・入力指紋を保存してから計算する。
既定深さ3（seedを1と数える）、最大5万候補で、上限に達した場合は `bounded` と表示する。
この探索規則で生成する候補を調べるもので、任意の論理式すべての全探索ではない。
未対応の自然文テーマは勝手に全集合へ置き換えず、集合名・式IDの指定を求める。

候補は独立した `X...` IDを持ち、親ときっかけになった単位を記録する。
親の反例・覆えなかった単位は `motivated_by` に累積し、それらを除いた評価も残す。
探索結果を既存の `propositions.toml` / `sets.toml` に自動採用しない。
同じデータから選んだ候補なので、独立データで確認済みとはしない。

依頼時のデータを `datasets/<結果SHA>/` に保存し、結果ブランチの更新後もそのデータで再開する。
保存済みデータが変わった場合や判定コードの指紋が依頼時と異なる場合は `blocked` とする。

## 導入

1. この実装と依存コードを、レビュー・承認後に既定ブランチ main へ統合する。
2. 受付専用のIssue番号を `AOI_INBOX_ISSUE` に設定する（初回は9）。`AOI_CYCLE` と `AOI_RESULTS_REF` を以下の表に従って設定する。初回は自動探索とLLMを無効のままにする。
3. `Aoi question inbox` を手動実行し、状態ブランチ作成と質問への返信を確認する。
4. `/explore E25` を投稿し、`Aoi bounded research worker` を実行する。

`contents: write` は状態ブランチ、`issues: write` は回答用。
変数が未設定なら両workflowとも処理しない。mainへの統合前はコメント受付も定期実行も稼働しない。

## ローカルLLM

`inbox.py` は `AOI_USE_LOCAL_LLM=1` のとき、規則で読めない `/ask` を
`http://127.0.0.1:8080/v1/chat/completions` のllama.cppへ渡せる。
JSON SchemaでQueryと未対応条件を返させ、Python側でも型を検証する。
この設定は質問の読み取りだけに使い、計算と回答の根拠は保存済み結果のまま。
モデルの解釈は完全ではないため、返信には読み取ったQueryも表示する。

既定のActions受付はモデルなし。リポジトリ変数 `AOI_USE_LOCAL_LLM=1` と以下を設定すると、
NagoyActionが同じrunnerでモデル確認・Docker起動・起動待ち・受付・終了を順に実行する。

- `AOI_LLAMA_IMAGE`: 公式 `ghcr.io/ggml-org/llama.cpp:server@sha256:...`（digest固定）
- `AOI_LLAMA_MODEL_URL`: 小型GGUFモデルのHTTPS URL
- `AOI_LLAMA_MODEL_SHA256`: そのモデルのSHA-256

モデルは `.models/model.gguf` に置き、既存ファイルのSHAが一致すれば再取得しない。
イメージdigestとモデルSHAは `.models/identity.json` に記録する。
`when_env` はその環境変数が1のときだけ手順を実行し、`always` の終了手順は先行手順が失敗しても実行する。
Docker Compose自体の機能を使い、別のコンテナ実行エンジンは作らない。
外部LLMのAPIキーは不要。LLMを起動しない場合も、対応する日本語と型付きJSONで利用できる。

## 検証

`uv run --frozen pytest QueRyu/tests/test_ask.py NagoyAction/tests/test_inbox.py PythDRagoras/tests/test_sets.py -q`

架空データによる実評価の中断・再開一致、候補数制限、未知条件、不完全な反例一覧、

## 依頼なしの自動運転

`research.toml` は `worker --seconds 18000` を呼ぶ。
Actionsでは受付Issueの設定が必要で、`AOI_RESEARCH_ENABLED=1` を追加すると自動探索を有効にする。
受付Issueだけの設定では手動依頼だけ処理する。自動探索は `AOI_RESEARCH_ENABLED=1` または CLI の `--autonomous` で有効にする。ワーカーを止めるにはGitHub Actionsで
research-workerワークフローを無効にする（実行中のジョブは別途キャンセル）。
`/stop` はその依頼と同じ入力・計画の自動探索も停止する。別の未停止の手動依頼は継続する。
終了済みなら「すでに終了」と返信し、停止記録を追加しない。

| サブプロジェクト | 自動運転での役割 | 再実行する条件 |
| --- | --- | --- |
| QueRyu ask | 判定済みID × 元・逆・裏・対偶 × 4種類の質問の回答を事前作成 | 判定結果または回答コードの変更 |
| PythDRagoras | 登録済み式を種に反例・未被覆の単位から候補を展開。その後、全登録集合の組み合わせ | 未処理候補が残っている、または入力・判定コードの変更 |
| DRAgoWing | 進捗・条件を満たした候補をHTMLにする | ワーカー開始時・5分ごと・探索終了時 |
| BlueProbe / QueRyu取得部 / SakAnalytics | 既存パイプラインによる取得・検査・集計を維持 | 本ワーカーから取得・集計を反復させない |
| NagoyAction | 起動・時間枠・状態保存・次回再開をまとめる | 定期実行・手動実行 |

既知回答は状態ブランチの `datasets/<結果SHA>/known/<fingerprint>/<ID>.json`。受付も同じ回答を再利用する。
除外球団など任意の追加条件は有限の事前作成の対象外で、受付時に同じ判定結果から答える。
データの変更後は以前の回答を使わない。

探索は登録順の式から始まり、全登録集合による探索へ進む。乱数もLLMも必要とせず、
入力・探索計画のハッシュで同じ仕事を再登録しない。1探索あたり深さ3、候補5万件が上限。
手動依頼を各巡回で先に処理し、自動探索は1件ずつ進める。各バッチ後に保存し、
5時間の処理枠に達したら終了して次の定期実行へ引き継ぐ。有限の探索範囲を全部調べた場合は
早く終了する。次回も入力を確認するが、同じ判定を時間いっぱい反復しない。

`public/index.html` と既知回答・探索結果はチェックポイントartifactにも収録される。
HTMLはダウンロードして開ける。GitHub Pagesへの公開はこの変更では設定していない。
グラフはPlotly CDNを使い、読み込めなくても数値表を表示する。
自動探索はIssueへの報告コメントを増やさず、手動依頼だけ完了返信する。
Docker/llama.cppは自然言語の読み取りが必要な受付パイプラインで起動し、その実行中は共有する。
自動探索・既知回答の作成ではモデルを起動しない。

## 球団年の比較から次の探索へ

自動運転の開始時、SakAnalytics の `baseball/neighbors.py` が保存済み `season.jsonl`
から、同リーグで A/B が異なる球団年の最近傍を探す。距離の指標は事前固定した
`rf_adv`・`ra_adv`・`vs_lower_wpct` の3つで、対象全体の標準偏差で標準化する。
各単位の最近傍を重複除去し、距離順の先頭20組を保存する。2012年（参照用）・設定の除外年・同率順位・
必要な値が欠ける単位は対象外にし、除外した単位も記録する。ばらつきゼロの指標は
距離から外す。距離を計算できる指標がなければペアなしとする。
これは相対的に近い組の抽出であり、類似の絶対的判定や有意差・因果関係の判定ではない。
特に下位相手との勝率は最終順位に依存する事後的な指標。

PythDRagoras の `logic/neighbor_checks.py` は各ペアを既存の命題・式の元の形の
反例一覧と照合する。反例一覧にない側を「成立」と推定しない。4つの形による
新しい候補の評価は既存の Explorer が担当する。

DRAgoWing は距離・関連命題の表とPlotly図を描き、そのHTMLの `report-data` に
同じ構造化観測を埋め込む。BlueProbe の `reports/dragowing_inspect.py` がこれを
オフラインで読み、ペアの追加・削除・変更と探索候補の変化を検出する。
JavaScriptの実行・外部URLへのアクセスはしない。未知の観測形式はエラーで止まり、
以前の観測を上書きしない。

HTMLから読み取れたペアに関係する登録済み式を、NagoyActionが次の探索で優先する。
同じ入力・計画で完了した探索は再投入しない。候補から子候補への展開はPythDRagorasが
反例・未被覆の単位に従って続ける。HTML側で新しい判定式を実行することはない。

`feedback/observations.json` に測定方法・対象外単位・ペア・照合結果、
`feedback/blueprobe.json` に最新観測、`feedback/history/` に差分履歴、
`feedback/priority.json` に優先する式を保存する。同じ入力では作り直さず、同じ観測を
履歴に重複追加しない。これらもチェックポイントartifactに含める。

## 返信失敗と件数の表示

返信は保存した結果から送る。1件のPOST失敗は `pending-replies/` に記録し、
後続コメントの受付・他の依頼の完了通知を続ける。失敗した同じ完了通知は同じworker実行で
反復送信せず、次回にコメント一覧を取り直してマーカーを確認してから再送する。
POST自体が成功して応答だけ失われても、次回は既存の返信を認識して二重投稿しない。
コメント一覧の取得に失敗したworkerは探索・保存を続け、通知は次回に回す。
状態の保存自体の失敗は処理を停止する（未保存のまま受付済みとはしない）。

`/status` はコメント由来の探索依頼の累積受付と、待機・進行/再開待ち・完了・
上限到達・停止・入力変更で保留・エラーを別々に表示する。複数の依頼を同じjobへ統合しても、
依頼の件数はコメント単位。自動探索を含む保存済みjob件数と返信再送待ち件数も別に表示する。
「進行/再開待ち」は保存済み状態であり、現在runnerが稼働中という保証ではない。


## 受付対象と負荷の上限

全コマンドは OWNER・MEMBER・COLLABORATOR、リポジトリ所有者、`github-actions[bot]` と指定したアカウントだけ受け付ける。
追加する人・Botはリポジトリ変数 `AOI_INBOX_ALLOWED_ACTORS` に `["claude[bot]", "指定したログイン名"]` のようなJSON配列で設定する。未設定なら追加アカウントはない。
受付対象外のコメントには返信・計算・記録を行わない。コメントイベントはworkflowの起動前にも判定し、定期読取りでも同じ判定を行う。
未完了・未停止の探索依頼は1人5件、全体20件まで。
上限を超えた依頼は理由付きで拒否し、完了・停止後に新しいコメントで依頼できる。
同じ入力・計画の計算は共有する。受付件数の上限は権限のあるBotにも適用する。
ワーカーは実行終了時に完了した依頼を最大20件ずつ1つのコメントへまとめる（残りは次回）。ランIDは `GITHUB_RUN_ID` を使い、ラン情報取得のAPIは呼ばない。
コメント一覧はまとめて1回だけ取得する（100件を超えればページ取得が必要）。実行中のバッチでは取得しない。
まとめを `notifications/` に投稿前に保存し、応答が失われても同じマーカーで再送確認する。次回に持ち越したまとめも同じ一覧で確認する。
HTML観測の失敗は前回観測を維持し `feedback/report-error.json` と `/status` に表示して探索を続ける。
成立率は元の判定結果、除外後の判例数は除外適用後と明記する。数が確定しなければ「不明」。
`/status` は保存された更新時刻の新しい順で最大10jobを表示する。

## サイクルと結果の指定（mainへの導入）

| 変数 | 既定値 | 用途 |
| --- | --- | --- |
| `AOI_INBOX_ISSUE` | 未設定（停止） | 受付Issue。初回は `9` |
| `AOI_CYCLE` | `c001-chunichi` | `cycles/<cycle>` の研究サイクル |
| `AOI_RESULTS_REF` | `cycle-001/chunichi` | 結果を読むブランチ・タグ・コミットSHA |
| `AOI_INBOX_ALLOWED_ACTORS` | `[]` | 追加で許可するログイン名のJSON配列 |
| `AOI_RESEARCH_ENABLED` | 未設定 | `1` のときだけ自動探索 |
| `AOI_USE_LOCAL_LLM` | 未設定 | `1` のときだけローカルLLMの読み取り |

手動実行の `cycle` / `results_ref` は、その実行だけ変数の値を上書きする。
Issueコメントからサイクルやrefは指定できない。別サイクルの受付へ切り替えても、
同じIssueの過去コマンドを未処理として読むため、通常はサイクルごとに専用Issueを使う。
同じサイクル内で結果refを更新しても受領済みコメントは再計算せず、新しいコメントで問い合わせる。

コードは既定ブランチをcheckoutする。結果refから取り出すのは `analysis.toml`、
`propositions.toml`、`sets.toml` と `outputs/season.jsonl`・`propositions.jsonl`・`sets.jsonl` だけ。
通常ファイルだけを許可し、結果側のPython・workflow・スクリプトは実行しない。
判定結果が存在しない場合は「結果が読めません」で停止し、別のサイクルへ代替しない。

状態ブランチは `aoi-research-state-c001-chunichi` のようにサイクルごとに分離する。
同一サイクルの受付同士・worker同士はそれぞれ直列化し、受付とworker間の保存は
既存のrebaseとpush再試行を使う。既知回答とキャッシュはデータSHAごとに分かれる。
受付記録、依頼、探索結果、返信にはサイクルと結果SHAを残す。既知回答のfingerprintには
回答コード・結果ファイル・target.jsonを含め、表示修正前の回答を再利用しない。

初回受付は既存コメントも読む。#9の既存 `/ask` 3件と `/status` 1件を動作確認に使い、
受領記録・返信を照合する。同じ受付を再実行しても、同じコメントへの返信を重複させない。
通常の議論やコードブロック内の試験案には反応しない。まとめ投稿は後続の変更で扱う。

停止するには `AOI_INBOX_ISSUE` を削除する。以後、両workflowの新しい処理は起動しない。
実行中のジョブも即時に止める場合はActionsからキャンセルする。状態は保持される。

回答では選んだ形（元・逆・裏・対偶）の成立率を表示し、除外時も分母を再計算しない。
来歴は「事後構成」「事前登録」「構成時期不明」と独立確認の状態を分けて表示する。
`posthoc: false` だけでは事前登録とせず、`registration.plan_sha` がある場合だけ事前登録とする。
独立確認ありは `confirmation.independent: true` と `confirmation.evidence_sha` の記録が必要。
既存データの誤った来歴は自動推定で訂正しない。研究側で根拠を確認してデータを更新する。
質問の来歴を含むHTMLは `public/answers.html` に保存する。

LLMの接続不能・時間切れ・不正応答は当該質問を判定不能として記録し、後続コメントを処理する。
規則とLLMの解釈が異なる場合も判定不能とする。終了や中断の例外は握りつぶさない。
モデルの準備に失敗した場合も受付と終了手順を実行し、パイプライン自体は失敗を記録する。
